Key findings logged as separate entries below.
- (constraint) lib.rs is vestigial: Cargo.toml has no [lib] or [[bin]] section, so Cargo auto-creates BOTH a bin target from main.rs (which has its own full 'mod audio/commands/store/tray/timer' + fn main with everything wired) AND a lib target from lib.rs (which just re-declares the same 5 modules, pub, with nothing consuming it -- no integration tests, no mobile entry point, Tauri v1 doesn't need one). Modules get compiled twice for no benefit. Likely leftover from a Tauri-v2-style template scaffold pasted onto a Tauri v1.5 project.
- (constraint) REAL bug found: serde casing mismatch. Rust structs (Station, Settings, AudioDevice in commands.rs) have no #[serde(rename_all = "camelCase")] and use snake_case fields (favicon_url, is_favorite, added_at, minimize_to_tray, output_device...). TypeScript interfaces (stores/playback.ts) expect camelCase (faviconUrl, isFavorite, addedAt). Tauri's default JSON serialization will not auto-convert casing -- station/settings data round-tripping through invoke() would silently fail to map fields both directions. This is more concrete and verifiable than the lib.rs claim it's replacing.
- (constraint) Confirmed still-broken: App.vue renders <router-view/> but package.json has no vue-router dependency and main.ts never installs a router. Main content area renders empty at runtime; only header + PlayerControls footer + SettingsModal show. Given the finalized UX spine (EXPERIENCE.md) is explicitly single-window/no-page-navigation by design, the fix is deleting <router-view/>, not adding a router.
- (constraint) Scope mismatch, existing backend vs finalized PRD: RadioPlayer/commands.rs implement a full 10-band biquad EQ (EqSource, BiquadFilter, set_eq_band/get_eq/reset_eq commands) and WAV recording (Recorder struct, start_recording/stop_recording commands, lame-sys + hound deps, native save-file dialog) -- both are explicit PRD Non-Goals (SS5). SettingsModal.vue/Settings struct carry output_device, buffer_size, eq_enabled, recording_format, recording_bitrate, compact_player -- none map to the finalized Settings surface (minimize-to-tray, Sleep Timer default, theme toggle). Tray + main.rs also wire global media-key Next/Prev station and tray Next/Prev menu items implying a linear-playlist skip model that doesn't match the finalized UX (list-click-to-play, no prev/next sequencing).
- (constraint) Scope gap, existing backend vs finalized PRD: no station-search/Directory integration exists at all -- stores/stations.ts ships a hardcoded DEFAULT_STATIONS array (~19 stations: SomaFM, Radio Paradise, KEXP, BBC, etc.) as a local fallback seed, not a Radio-Browser API client. FR-1 (search) is entirely unbuilt. No Location/Weather/Stream-Info-tile backend support exists (Metadata struct only carries ICY title/artist/album/artwork, no codec/bitrate/IP/coordinates fields).
- (constraint) Visual paradigm mismatch confirmed: existing Tailwind usage (PlayerControls.vue, SettingsModal.vue, App.vue) is light-first with dark: variants, rounded-xl cards, colorful gradient icons, red/green transport buttons -- the opposite of DESIGN.md's flat/near-black/violet-blue/no-shadow/2px-radius Metro aesthetic. Store's local JSON persistence (store.rs), SleepTimer's oneshot-cancel pattern (timer.rs), and Tray's menu/window-event wiring (tray.rs, minimize-to-tray in main.rs) are structurally sound and match FR-10/FR-11/FR-12 needs, modulo data-shape changes. vite.config.ts/tsconfig.json/tailwind.config.js (the @ alias, darkMode:'class') are correctly wired and worth keeping as-is.
- (decision) Tauri version: staying on 1.5 (ADOPTED, not upgrading to Tauri v2). Verified v2.10.1 is the actively-developed current stable line as of March 2026 and is generally recommended for new projects (mobile support, current release cadence) -- but v2's headline benefit (mobile) is irrelevant for a Windows-only personal app, and the v1->v2 migration (different permission/capability system, different command registration) is real work for no functional gain. User confirmed this lean.
- (version) Verified external dependencies still sound: Radio-Browser API (all.api.radio-browser.info) is free, no-auth, actively maintained community directory. Open-Meteo (open-meteo.com) is free with no API key for non-commercial use, 10k calls/day cap -- nowhere near what a single-user app needs.
- (question) User directly questioned whether the Tauri+Vue+Rust stack choice itself was sound, given the prior agents' failure. Investigated via web: verified Tauri idles at ~30-80MB RAM / ~3-10MB bundle vs Electron's ~150-400MB RAM / ~120-200MB bundle (2026 benchmarks). Electron would blow past the PRD's own NFR-2 idle-RAM target (~150MB) from its baseline alone, before the app even does anything. Conclusion: the STACK CHOICE was sound and is confirmed, not the source of the problem.
- (decision) Root cause of prior fragility identified, NOT the stack: audio/player.rs hand-rolled its own ICY-metadata byte-parser and HTTP streaming Iterator that calls tokio::runtime::Handle::current().block_on() INSIDE Iterator::next() (a blocking call inside what rodio treats as a synchronous pull) -- a genuine anti-pattern and likely source of instability. This duplicates functionality of stream-download (already an UNUSED declared dependency in Cargo.toml at v0.5!) paired with the purpose-built icy-metadata crate. Verified both are current and actively maintained: stream-download v0.24.3 (Aug 2026), icy-metadata v0.6.0 (Jun 2026) -- icy-metadata's own dev-dependencies confirm it's specifically designed to pair with stream-download + rodio for exactly this Icecast-streaming use case. AD: replace the hand-rolled HttpStreamSource/parse_icy_metadata with stream-download (bump to 0.24) + icy-metadata (add 0.6), eliminating ~150 lines of fragile hand-written async/iterator-blocking code for two well-tested purpose-built crates. No footprint or stack-level cost -- pure internal simplification, directly serves 'least overhead.'
- (decision) Repair-vs-rebuild resolved (user confirmed hybrid, 'least overhead' framing): KEEP and extend Rust audio/store/tray/timer core (fix serde casing, swap in stream-download+icy-metadata, strip EQ/recording, delete vestigial lib.rs). REWRITE the Vue frontend from scratch against DESIGN.md/EXPERIENCE.md -- existing Vue markup shares almost nothing with the target IA or visual language, not worth patching.
- (decision) Design paradigm: Layered architecture (user confirmed). Vue components -> Pinia stores -> Tauri command boundary (the ONLY frontend/backend crossing point, no direct fetch() from Vue to Radio-Browser/Open-Meteo) -> Rust services (player, directory client, weather client, store, timer, tray) -> external I/O (HTTP APIs, OS audio, filesystem). Folders stay flat-by-type (components/, stores/, services/ on Rust side) -- explicitly rejected feature-sliced folders as unneeded ceremony for ~6 features on a solo project.
- (decision) State sync model: push via Tauri events (user confirmed), not frontend polling. Rust emits an event whenever playback/metadata state changes; Pinia stores are a read-model that listens, never polls. Matches Tauri's native pattern, avoids wasted cycles for a tray-resident always-open app.
- (decision) Data shape changes (user confirmed, 'yes ok for now'): Station gains genre/country/language (replacing single category field, native Radio-Browser fields, needed for FR-1 Filter) plus optional codec/bitrate/geo_lat/geo_long (native Radio-Browser fields, feed Stream Info + Location tiles). Resolved stream IP is explicitly NOT persisted on Station -- it's runtime-only, computed live during playback. Settings struct drops output_device/buffer_size/eq_enabled/compact_player/recording_format/recording_bitrate (all serve non-goal EQ/recording features) down to just minimize_to_tray, sleep_timer_default_minutes, theme. Every Rust struct crossing the Tauri command boundary gets #[serde(rename_all = "camelCase")] as a blanket rule, not a one-off patch.
- (decision) AD: each Info Tile's data (now-playing metadata, location, weather, stream info) is pushed as its OWN independent Tauri event, never one bundled payload. Prevents a slow weather/location fetch from delaying metadata or blocking the dashboard -- this is the concrete mechanism behind NFR-3's 'tiles degrade independently' promise, not just a UI-layer note. User confirmed.
- (decision) Deployment/operational envelope (user confirmed, explicitly required to not be left silent): single environment (the user's own PC), no server component ever -- Rust calls Radio-Browser/Open-Meteo directly over HTTPS. Build via 'tauri build' to a Windows installer, x86_64 target. No auto-update, no code signing, no CI pipeline -- all deliberately deferred as unneeded ceremony for a single-machine personal app. Unsigned-installer SmartScreen warning is an accepted cost. No telemetry/crash reporting -- this one is inherited from PRD NFR-5 (privacy), not merely deferred.
